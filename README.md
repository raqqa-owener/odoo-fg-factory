# ERP Specification to Odoo / Knowledge Graph PoC

Dynamics 365系のERP導入・業務仕様書を構造化し、Odoo標準機能とのFit & Gap、関連モデル、追加実装候補を検証するために開発したPoCです。

本リポジトリは完成したERP移行製品ではありません。将来、ERP資料を検索可能な基礎データへ変換し、追加開発時の影響範囲調査や、開発ベンダーへ渡す資料の生成に利用できるかを検証した途中成果です。

## 解こうとした課題

ERPの追加開発では、既存資料、業務要件、テーブル、画面、権限、承認経路が分散し、影響範囲の調査とベンダーへの仕様伝達に大きな工数がかかります。

このPoCでは、次の仮説を検証しました。

1. Dynamics 365の一般的な導入・業務仕様書を構造化して読み取る。
2. 構造化した要件をOdooの標準モデル・機能へ対応付ける。
3. 標準で対応できる項目と、追加開発が必要なFit & Gapを分離する。
4. モデル、項目、業務テーマなどの関係をKnowledge Graphとして保持する。
5. 顧客への確認事項、内部設計、Odoo実装候補を同じデータから生成する。

## 生成AIの利用方法

元資料の読解と構造化JSONの作成には、OpenAI APIを組み込んだ自動処理ではなく、ChatGPT上で作成した目的別プロンプトを使用しました。

PoC段階で大量の資料をAPIから繰り返し処理するコストを避け、まず対話的に抽出方法と構造を検証するためです。

ChatGPTが担当したのは、資料の意味解釈と構造化候補の作成です。その後のJSON取込、スキーマ検証、参照整合性確認、Fit & Gapの分離、Neo4jへのdry-run／適用、Odoo実装候補への変換は、再現可能な決定論的コードとして実装しました。

生成AIに完成した仕様書を一度で作らせるのではなく、確率的な意味解釈と、コードによる検証・適用制御を分離しています。

## PoCで検証した範囲

- 構造化JSONおよびPackの取込
- スキーマ・参照整合性の検証
- dangling relationshipの検出
- Odoo標準置換候補とFit & Gapの分離
- Neo4jへのdry-runおよび適用
- 顧客確認用Question Packの生成と回答の再取込
- 内部設計Packの取込・検証
- Odooアドオン生成用データへの変換
- 非破壊的なOdooオーバーレイ／デモアドオンの生成検証

詳細は [公開HANDOFF](docs/PUBLIC_HANDOFF.md) と [アーキテクチャ](docs/ARCHITECTURE.md) を参照してください。

## 到達していない範囲

次の機能は将来構想であり、このPoCでは完成していません。

- ERP原本をRAGで横断検索する本番パイプライン
- 任意の追加開発要求から影響範囲を自動確定するエージェント
- 完成したベンダー向け追加開発仕様書の全自動生成
- Dynamics 365からOdooへの全面移行
- 本番利用を前提とした認証・監査・運用機能

別プロジェクトを優先したため、このPoCはいったん現在の段階で停止しています。

## 将来構想

ERPの導入資料、業務仕様書、テーブル定義などを構造化し、追加開発要求を受けたエージェントが、関連する業務機能、モデル、テーブル、項目、画面、権限、承認経路、既存アドオンを調査します。

その結果を基に、顧客への確認事項、影響範囲、実装候補、テスト観点を整理し、開発ベンダーへ渡す追加開発資料を生成する構想です。

もう一つの応用として、テーブル構造と項目間の関係を基に、自然文の質問から必要なデータを特定し、適切なJOINを含むSQLを組み立てることも想定しています。

この自然文からのデータ検索については、別プロジェクトで、SQLの生成・実行、分析グラフ、分析文の自動生成まで実装し、納品を完了しています。本リポジトリに当該案件の顧客データやソースコードは含めていません。

## 関連する現在の開発

### Odoo Launchpad

ローカルで開発したOdooカスタマイズPackを投入し、Terraformを利用してAWSへデプロイする仕組みを開発しています。実案件を使った本番環境への初回デプロイと起動まで完了しています。

- 稼働環境: https://odoo-inquisitor.rakka.co.jp/inquisitor
- 次の工程: GitHub Actionsによる検証・反映・再デプロイの自動化

### Odoo Screen Builder for Figma

Odooのモデル、フィールド、継承ビュー、タブ、グループ、ボタン、表示順、配置関係などを「画面構造」として定義し、Neo4jへ格納します。その構造データから編集可能な画面骨格を生成し、Figmaへ反映するPoCです。

新しい画面を追加するときは、エージェントがOdooのデータベース、モデル、ビュー定義などから必要な情報を取得し、画面生成に必要な処理と確認工程を組み立てます。その結果を画面単位のZIPとして出力し、Screen Builderへ取り込むことで画面を追加する方式を独自に考案しました。画面ごとの差分を個別実装ではなく、構造データと再利用可能なPackとして扱うことで量産化を目指しています。

一画面の生成技術とZIP取込を前提とした量産基盤を構築し、現在は異なる種類の複数画面を安定して生成できるかを検証しています。Odoo画面の調査、構造化、Figma上での再作成、画面部品配置にかかるデザイナー作業を90%以上削減できる可能性を検証しています。
